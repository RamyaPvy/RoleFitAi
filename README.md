# RoleFit AI

RoleFit is becoming a public, multi-user job-search workspace. This first application foundation replaces the local-only demo with Supabase authentication and database-enforced private candidate profiles.

## Current scope

- Email/password sign-up and sign-in through Supabase Auth.
- Server-side session cookies, protected profile page, and sign-out.
- A candidate profile stored in a per-user PostgreSQL row protected by Supabase Row Level Security (RLS).
- Server-side input validation and a typed database contract.
- No service-role key, employer credentials, or other server secret is exposed in browser code.
- Private resume storage: upload, download (short-lived signed link), and delete PDF/DOCX files (max 5 MB, up to 10 per user) in a private Supabase Storage bucket protected by RLS.
- Job discovery: public employer job boards (Greenhouse, Lever, Ashby; ~180 companies) plus the Remotive and Arbeitnow feeds, synced by `POST/GET /api/jobs/sync` (a Vercel cron in `vercel.json` runs it every 6 hours). The Job matches page filters by job titles (with related titles), posted date (24h to any), location, and keyword, newest first, with paging. Resume skills are not used to filter results.
- Resume tailoring: per job, the built-in free engine rearranges your own uploaded resume for the posting (relevant skills and bullets first, a short "Applying for" summary), renders a PDF, and saves it privately as `Company_YourName_Resume.pdf`. It never adds facts; requirements your resume does not show are listed as gaps. Setting an optional `ANTHROPIC_API_KEY` switches to Claude-written wording, with invented skills and numbers filtered out.
- Application ledger: save jobs, record which resume you used, and track status and notes.
- No automatic application submission is connected (see the boundary below).

The earlier fictional sample profile, job feed, downloaded demo file, and browser-local application tracker have been removed. Start with your own profile; don't put sensitive resume details in this project until you connect and configure your own Supabase project.

## Run locally

Requirements: Node.js 20.9 or later and npm.

For the complete beginner-friendly Windows guide, follow [GETTING-STARTED.md](./GETTING-STARTED.md). In short:

1. Create a Supabase project.
2. Configure `.env.local`, apply the profile database migration, and allow the local auth callback.
3. Run `npm install` and `npm run dev`.
4. Open `http://localhost:3000`.

Without Supabase configuration the app shows setup instructions and disables account forms; it does not silently store candidate data in browser storage.

## Security model

- Every profile is keyed to the authenticated Supabase user ID. RLS allows candidates to select, insert, or update only their own row.
- Database access uses the public publishable key plus the candidate's authenticated session. The RLS policy is the authorization boundary; hiding UI is not treated as access control.
- Server actions authenticate and validate submitted form data before writing it. The profile is read through a server-side Supabase client.
- Supabase email confirmation and abuse protections should be configured before public launch. Configure CAPTCHA/rate limits and account recovery in the Supabase project before opening registration broadly.
- Use HTTPS in production, set `NEXT_PUBLIC_SITE_URL` to the deployed origin, and add only the required production callback URL to Supabase Auth's redirect allowlist.
- Supabase controls session refresh and expiry. The app does not promise indefinite sessions.
- Resume files are stored in a private bucket with per-user RLS policies. This foundation does not yet handle account deletion, privacy exports, retention, or a production privacy policy. Complete those before accepting real resumes at scale.

## Automatic application boundary

The product direction is automatic applications **only for employers who authorize RoleFit**. The current code does not connect to any employer, job board, ATS, or application endpoint. Do not represent a job as OPT-friendly or an application as submitted without reliable source evidence.

Employer/job-platform APIs distinguish reading public job listings from submitting a candidate application. For example, Greenhouse application submission requires an employer board API key; Lever's submission API uses an API key generated by an employer's Super Admin; and Ashby's submit endpoint requires a key with `candidatesWrite` permission. Public job listing access is not permission to submit for every employer. Integrations must be enabled per employer with their authorization, credentials kept server-side, dynamic form requirements respected, and a candidate confirmation/audit record retained.

Until a participating employer authorizes an integration, an application can be prepared for the candidate to review and complete on the employer's official site; it must not be auto-submitted. No ATS score or interview outcome can be guaranteed.
